# Build Prompt Generator

A single-screen web application: add a requirements file, paste a description or requirements, or do
both, and get a draft build prompt back that you can revise, copy or download. Nothing you enter is
stored.

## What it does

**Inputs.** Two input modes on one screen, usable separately or together:

- One or more uploaded files, dropped onto the page or chosen through the file input.
- Pasted free text in a labelled requirements field.

Uploaded files are read on the server: `.txt`, `.md`, `.markdown`, `.pdf` and `.docx`. A file's kind
is decided from its extension and then confirmed from its leading bytes, never from the MIME type the
browser declares — a mislabelled file is refused rather than routed to the wrong parser.

**Output.** A draft build prompt — Markdown written by a hosted language model from the sources you
supplied, following a fixed eight-section skeleton:

1. Overview
2. Goals and Non-goals
3. Functional Requirements
4. Non-Functional Requirements
5. Technical Constraints and Preferred Stack
6. Deliverables
7. Acceptance Criteria
8. Open Questions

Functional requirements are numbered, and any section the supplied source does not support is marked
`[NEEDS CLARIFICATION: …]` rather than filled with invented content.

The draft streams into the editor while the model writes, so there is no wait for a finished
document. It is editable in place with a live character count; you can copy it to the clipboard or
download it as `build-prompt-<yyyyMMdd-HHmmss>.md`. A generation in progress can be stopped, which
cancels the browser request and the upstream model call together, so an abandoned draft is not paid
for.

**Nothing is stored.** There is no database, no disk write, no cache and no session: your inputs and
the draft exist only in the browser tab. The request log carries counts, durations and codes, never
your document or prompt text.

## Prerequisites

- **Node.js ≥ 22.22.2.** This is a hard floor, not a suggestion: it is the strictest `engines`
  requirement in the dependency tree and `package.json` declares it.
- **npm ≥ 11.21.0.**

## Installation and running

```bash
npm ci                        # reproducible install from the committed package-lock.json
cp .env.example .env.local    # then set the values your deployment needs
npm run dev                   # local development
```

For a production-mode run:

```bash
npm run build
npm run start
```

`package-lock.json` is generated by the first `npm install` and committed, so `npm ci` resolves the
same dependency tree on a fresh checkout.

A real `OPENAI_API_KEY` is needed only to generate against OpenAI. The whole test suite, and a local
development run (`npm run dev`) with `PROMPT_PROVIDER=stub`, need no credential and make no outbound
request. A production-mode run (`npm run start`) refuses the stub provider, because `NODE_ENV` is
`production` there.

## Environment variables

A copy of this contract lives in `.env.example`, which you copy to `.env.local`. That file holds
secrets and is never committed.

| Variable          | Required                 | Default      | Behaviour when unset / notes                                                                                                                                                                                                                                          |
| ----------------- | ------------------------ | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OPENAI_API_KEY`  | required at request time | none         | Read server-side only: never exposed through a `NEXT_PUBLIC_` variable and never logged. | `OPENAI_MODEL`    | optional                 | `gpt-6-luna` | Overrides the model string used for the Responses API call.                                                                                                                                                                                                           |
| `PROMPT_PROVIDER` | optional                 | `openai`     | `stub` selects the deterministic, no-network provider used by the tests and by local development. | `PORT`            | optional                 | `3000`       | Consumed by `next start` and by the Playwright base URL.                                                                                                                                                                                                              |
| `NODE_ENV`        | set by the framework     | —            | Read by the provider guard that refuses `stub` in production. A deployment does not set it, so it is documented here rather than in `.env.example`.                                                                                                                   |

## Architecture

One deployable serves both the page and the one endpoint, so the provider credential stays
server-side without a second service to authenticate.

**Browser — client component tree.** `src/components/PromptGenerator.tsx` owns the screen's state and
request lifecycle (idle → validating → extracting → streaming → done or error), builds the
`FormData`, POSTs it, and consumes the response stream through the shared parser in `src/lib/sse.ts`.
`FilePicker.tsx`, `DraftPanel.tsx` and `StatusBanner.tsx` are presentational and receive props. The
client imports only types (`src/types/index.ts`) and the stream codec from `src/lib`; the limits its
pre-checks use arrive as props from the server page, so the validation module and its `zod`
dependency never enter the browser bundle.

**Server — one stateless route handler.** `src/app/api/generate/route.ts` owns the whole server-side
sequence for a request, and nothing survives it:

```text
Content-Length guard → validateSubmission → extractDocument → buildSourceBundle →
checkRateLimit → renderInput → getProvider().generate → SSE frames
```

The handler keeps no module-level mutable state, no cache and no memoised provider, so a second
instance needs no coordination. The only cross-request state in the process is the rate limiter's
(see [Known limitations](#known-limitations)).

### The generation endpoint

`POST /api/generate`, same origin, `multipart/form-data` up and `text/event-stream` down. The request
carries `description` (optional text) and one or more `files` parts. The response is a stream of
frames: exactly one `meta`, then zero or more `delta`, then exactly one terminal `done` or `error`.

| Frame   | Payload                                                                      | Meaning                                                                                                                             |
| ------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `meta`  | `documents[]` (name, chars, truncated), `sourceChars`, `warnings[]`, `model` | Sent before generation starts: which files were accepted, truncated or refused.                                                     |
| `delta` | `text`                                                                       | One piece of the draft, appended in order.                                                                                          |
| `done`  | `chars`, `model`, `durationMs`, `truncated`                                  | Terminal success. `truncated: true` means the model was cut off at the output cap, so the draft is partial and is labelled as such. |
| `error` | `code`, `message`, `retryable`                                               | Terminal failure after streaming began.                                                                                             |

Frames are `data: <json>` followed by a blank line. `: ping` comment keepalives are written every 15
seconds while the model works, and consecutive small deltas are coalesced so each write reaches the
socket at ≥ 1 KB, which is what keeps a browser from buffering a small-chunk stream.

**Failure responses** are JSON `{ code, message, retryable }`, sent only before streaming begins:

| Status | Code                   | When                                                                                                         |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| 400    | `INVALID_INPUT`        | The pasted description is over its 10,000-character limit, or nothing usable arrives after extraction.       |
| 413    | `PAYLOAD_TOO_LARGE`    | `Content-Length` is over 16,777,216 bytes, refused before the body is read.                                  |
| 429    | `RATE_LIMITED`         | More than 10 requests from one client identity within 600,000 ms; the message states when the window resets. |
| 500    | `INTERNAL_ERROR`       | An unexpected failure, reported with a generic message that leaks no internal detail.                        |
| 503    | `PROVIDER_UNAVAILABLE` | `OPENAI_API_KEY` is missing, or the provider refused or failed before the first token.                       |

Two further codes can only occur once the status line is already on the wire, so they travel as an
in-stream `error` frame instead: `PROVIDER_ERROR` (the provider failed after the first token) and
`GENERATION_TIMEOUT` (the handler's own 90-second deadline fired; it aborts the provider call and
writes the frame itself).

### Limits, under one rule

One rule decides every limit breach.

**A request-level violation fails the request:**

- Body over 16,777,216 bytes (16 MiB) → 413, refused from `Content-Length` before the body is read.
- Pasted description over 10,000 characters → 400.
- Nothing usable after extraction → 400.

**A file-level violation becomes a warning and the rest of the submission proceeds:**

- More than 5 files.
- A file over 8,388,608 bytes (8 MiB).
- An unsupported type.
- A file that cannot be read.
- An extraction that comes back empty.

Independently, the assembled source is capped at 60,000 characters, counted description-first, with
per-document truncation reported in the `meta` frame. Generation is bounded by the handler's own
90-second deadline; `maxDuration = 90` sits beside it only as a hosting hint that stops a platform
killing the invocation before that deadline can write its terminal frame.

### Security and privacy posture

Uploaded and pasted content is untrusted data: it is fenced, provenance-labelled and JSON-encoded
inside an unambiguous delimiter, placed in the user message only and never in the system instruction,
which states that document content is data to describe rather than instruction to follow. Prompt
injection has no reliable filter, so it is contained architecturally rather than detected. The
provider credential is read only in server modules.

Generated Markdown is untrusted output: it is displayed as text in a textarea, so no HTML, image or
link preview is ever rendered from model output. `next.config.ts` sets four security response headers
on every route — `X-Content-Type-Options: nosniff`, `Referrer-Policy:
strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and `Permissions-Policy: camera=(),
microphone=(), geolocation=()`. A nonce-based content security policy is deliberately not added:
Next.js needs inline bootstrap scripts, a static policy would either break hydration or degrade to
`unsafe-inline`, and rendering the draft as text already removes the cross-site-scripting surface a
CSP covers.

Request caps and the per-source rate limit bound what a request can cost, independently of the
model's context window. Nothing entered is persisted anywhere.

## Tests

```bash
npm run test                      # unit and integration
npm run test:coverage             # the same, with coverage thresholds
npx playwright install chromium   # once, before the first end-to-end run
npm run test:e2e                  # end-to-end
```

- **Unit suites** cover validation, extraction, source assembly, the prompt template, rate limiting,
  the stream codec, error mapping and the two interactive components.
- **Integration** drives the route handler end to end with the stub provider, across the success path
  and each error status.
- **End-to-end** is one Playwright happy path — paste requirements, generate, see the draft, copy it,
  download it — against a server the config starts itself with `PROMPT_PROVIDER=stub`.

No suite needs a network, a credential or wall-clock timing: the provider is stubbed, the rate
limiter's clock is injected, and the end-to-end run starts the application in stub mode.

**Coverage contract:** ≥ 80% lines for `src/lib/**` and `src/app/api/**`, enforced by
`vitest.config.ts`.

## Known limitations

1. **The rate limiter is in-memory, so it is per instance.** It allows 10 requests per 10 minutes per
   client identity. Behind a load balancer with more than one instance the effective limit
   multiplies, and a restart clears every count. A shared store (Redis or a hosted limiter) is
   deliberately out of scope for a single-instance tool.
2. **The rate-limit key depends on the client identity the deployment can be trusted to supply.** It
   is the connection's socket address where the runtime exposes one, and otherwise a single shared
   bucket. `x-forwarded-for` is honoured only behind a proxy known to overwrite it — as a bare header
   it is client-settable, and trusting it by default would let one caller rotate identities straight
   past the limit.
3. **`.docx` extraction is covered by a mocked reader rather than a committed binary fixture**, so the
   Word path is exercised without shipping a binary test asset.

## Scope

This product deliberately does not do the following, and nothing in the repository implements them:
no persistence, history or accounts of any kind; no model providers beyond OpenAI plus the
deterministic stub, and no model or temperature picker; no document formats beyond the five listed;
no Markdown rendering or non-text export; no resumable streams or server-side draft state; no UI for
editing the system instruction or the section skeleton; no analytics, telemetry or error-reporting
service; no container, CI/CD pipeline, infrastructure automation or deployment scripts; and no
third-party script, font or stylesheet — the page loads nothing cross-origin.
